# Using Interlint

How to set Interlint up in a project, what `interlint.yaml` holds and how the checks run. For the agent side, see [OpenCode](opencode.md) and [Claude Code](claude-code.md).

## Install

Requires Node 22 or later.

```bash
npm install -g interlint
```

`interlint` is then on your `PATH`, where the OpenCode plugin and the Claude Code hooks look for it. To run a build of this repository instead, see [Development](development.md).

## `interlint init`

Run it in the root of your Maven project, or of a workspace that holds several (see [Multi-module projects and workspaces](#multi-module-projects-and-workspaces)), with the agent you use (`opencode` or `claude-code`):

```bash
interlint init --agent opencode
```

`init` looks for the test classes under `src/test/java` that use `@ArchTest`, and for `maven-checkstyle-plugin` and `maven-pmd-plugin` in the build of `pom.xml`. It writes an `interlint.yaml` with one check for each thing it finds:

```yaml
# Generated by interlint init.
checks:
  - name: architecture
    run: ./mvnw -q test -Dtest=ArchitectureRulesTest -Dcheckstyle.skip -Dpmd.skip
    report: archunit
    when: edit
  - name: checkstyle
    run: ./mvnw -q checkstyle:check
    report: maven
    when: edit
  - name: pmd
    run: ./mvnw -q compile pmd:check -Dcheckstyle.skip
    report: maven
    when: edit
```

- The checks use the project's Maven: `./mvnw` when the project has the Maven Wrapper, `mvn` otherwise. The file is the same on every machine, so commit it: with `mvnd` the checks run after each edit, without it at task end (see [After each edit](#after-each-edit)). `init` says which applies on yours.
- It never replaces a different `interlint.yaml` unless you pass `--force`. Running it again on an unchanged project changes nothing.
- The `architecture` check runs only the `@ArchTest` classes. `checkstyle` and `pmd` run the project's own `check` goals, each in its own Maven call: in one call, a failing goal stops the ones after it. `pmd` compiles first because PMD resolves types from the compiled classes. See [Checkstyle and PMD](#checkstyle-and-pmd).
- Each check skips the plugins the other checks run (`-Dcheckstyle.skip`, `-Dpmd.skip`), so a failure shows in one check only. Without that, a build that binds `checkstyle:check` to an early phase such as `validate` would stop `test` and `compile` before ArchUnit or PMD run, and show Checkstyle's failures under their names. Without Checkstyle or PMD in the build, the `architecture` check has no `-D…skip`.
- When the build runs a plugin's `check` goal in an `<execution>`, the check names that execution, as in `checkstyle:check@style`, so the configuration inside it applies: called plainly, Maven runs the goal with the plugin's defaults. An execution without `<id>` is `default`; one turned off with `<phase>none</phase>` is left out.
- A plugin counts when it is in `<build>`, in `<plugins>` or `<pluginManagement>`. Plugins only in a comment, a `<profile>`, `<reporting>`, `<dependencies>` or `<dependencyManagement>` are left out, and so are plugins declared only in an external parent. In a project with modules, see [Multi-module projects and workspaces](#multi-module-projects-and-workspaces).
- With no `@ArchTest` classes and neither plugin it says so, writes nothing and exits with 2.
- `--agent opencode` also copies the OpenCode plugin. See [OpenCode](opencode.md).
- `--agent claude-code` also adds Interlint's hooks to `.claude/settings.json`. See [Claude Code](claude-code.md).
- At the end it prints what it detected and which files it wrote or left unchanged. `--cwd <dir>` runs it on another directory.

The generated file is yours: edit it to change `when` or the command.

## `interlint check`

Run the checks by hand:

```bash
interlint check --when task-end
```

It prints nothing and exits with 0 when every check passes. Otherwise it prints each violated rule, with the text of its `because()` and every violation with its source file and line:

```text
✗ architecture · ARCH-01: domain depends on nothing outside domain

  Method <com.acme.domain.Order.toEntity()> calls constructor <com.acme.infra.OrderEntity.<init>()> in (Order.java:27)
    at src/main/java/com/acme/domain/Order.java:27

Fix these problems before continuing.
```

| Exit code | Meaning |
|---|---|
| 0 | Every check passed |
| 1 | A check failed: violations, a command that failed without leaving any, an ArchUnit command that wrote no report, or broken compiled classes |
| 2 | Configuration or usage error, or an unexpected Interlint error |

### Broken compiled classes

An IDE that builds automatically, such as VS Code with the Java extension or Eclipse, compiles into the same `target/classes` as Maven. If it writes there while a check runs, ArchUnit reads classes compiled with unresolved types and reports violations the code does not have: a domain class that depends on `<ProjectName>`, a service that implements no port. The types are named without a package, which `javac` never compiles. When a violation names one, Interlint shows no violation of that check and says the build is broken instead:

```text
✗ architecture · the compiled classes are broken, so its ArchUnit violations are not shown

  The report names types without a package: <ProjectName>, <ProjectStatus>.
  javac never compiles a class like that. Another compiler, usually an IDE building automatically,
  wrote to target/ while the check ran. Do not change the code for these violations.
  Turn off the IDE's automatic build for this project, or run the build with clean, and check again.
```

Maven does not recompile those classes by itself, since they are newer than their sources, so the check stays broken until a build with `clean`. In VS Code, `"java.autobuild.enabled": false` in the project's settings stops the IDE from writing there. A rule that analyzes classes of the default package would show the same message, since their names have no package either.

On Windows, a leading `./` in `run` becomes `.\`, so the same `interlint.yaml` works on every operating system.

## Checkstyle and PMD

A check with `report: maven` reads the reports Checkstyle and PMD write in `target/`: `checkstyle-result.xml` and `pmd.xml`, in the project and in its modules, at any depth. Each violated rule shows its message and source file and line, like an ArchUnit rule:

```text
✗ checkstyle · LineLength

  Line is longer than 80 characters (found 87).
    at src/main/java/com/acme/domain/Order.java:8

Fix these problems before continuing.
```

- The project's build decides, not Interlint. The reports also list what the build accepts, such as warnings under Checkstyle's `violationSeverity` or violations under PMD's `failurePriority`. So a `report: maven` check fails only when Maven fails. When Maven exits 0 it passes, with or without a report: the build may skip the plugin, for example with `<skip>true</skip>` outside CI.
- When Maven fails, only the most severe level in the reports is shown: Checkstyle `error` before `warning` and `info`, the lowest PMD `priority` number first. That level always failed the build, so nothing the build accepts is shown. Less severe failures, if any, show on the next run.
- A report counts only when Maven says its plugin's `check` goal failed. When Maven fails for another reason, such as code that does not compile, the check shows the last lines of Maven's output instead.
- Messages are in the language of the JVM, as Checkstyle and PMD write them.

## After each edit

A check with `when: edit` also runs after the agent changes one of its sources:

```bash
interlint check --when edit --file src/main/java/shop/Order.java
```

- Only `edit` checks run, and only when a changed file inside the project is one of their sources: `*.java` for `report: archunit` and `report: maven`. Any other file, such as `README.md`, runs nothing and exits with 0.
- The output and exit codes are the same as at task end. `--file` can be repeated.
- With [`mvnd`](https://github.com/apache/maven-mvnd) on the `PATH`, a check whose `run` starts with `mvn`, `mvnw` or `./mvnw` runs with `mvnd` instead, with the same arguments, at edit time and at task end. Keep `./mvnw` in `interlint.yaml` so it works for teammates without `mvnd`.
- Without `mvnd`, Maven `edit` checks do not run after edits, because a cold Maven build takes several seconds; they still run at task end.
- A `report: maven` check shows only the failures of the changed files: Checkstyle and PMD rate each file on its own, so another file's failures are not the edit's, and task end shows them. When Maven failed only because of other files, the check passes after the edit. An ArchUnit check shows every failure, because an edit can break a rule in a class it did not change.
- A `run` with `checkstyle:check` gets `-Dcheckstyle.includes` with the changed files' paths from their source root, such as `shop/Order.java`, so Checkstyle checks only them, still with the build's configuration. PMD cannot be limited from the command line, so it checks the whole project. Checkstyle also checks the whole project when the `run` sets `checkstyle.includes` itself, or when the plugin's configuration in `pom.xml` sets `<includes>`, which Maven applies over `-D`.
- Check runs on the same project never overlap: a second edit waits until the first one's checks finish.

## At task end

Every check runs, `edit` ones included. A project whose checks all pass is remembered as passing, with its files as they are.

```bash
interlint check --when task-end --changed
```

With `--changed`, only the checks of the projects that changed since their checks last passed run. The OpenCode plugin and the Claude Code `stop` hook use it, so the end of a task does not run the checks of a project nobody changed. A project is a check's `dir`, or the directory of `interlint.yaml` for a check without one. It counts as changed when:

- an edit check call (`--when edit`, which the agent integrations run after every edit) named one of its files, whatever the file is; or
- a file was added, changed or removed since its checks last passed, by any means, such as a shell command. Build output (`target/`), `node_modules/` and hidden directories such as `.git/` do not count. A commit does not count either: it leaves the files as they are.

With `--file <path>`, which can be repeated, only the projects that hold one of those files run. The agent integrations pass the files a subagent changed, so it gets the failures of its own projects only:

```bash
interlint check --when task-end --changed --file orders/src/main/java/shop/Order.java
```

A project Interlint has not seen before counts as unchanged until something above happens, so the first task end does not run every project. A project whose checks fail stays changed, so they run again at the next task end, and so does a project changed while its checks ran, by an edit or any other means: a project is remembered with its files as the checks saw them. A check that writes files outside `target/` therefore makes its project run once more at the next task end. The state is kept in your user's state directory (`%LOCALAPPDATA%\interlint\projects` on Windows, `$XDG_STATE_HOME/interlint/projects` or `~/.local/state/interlint/projects` elsewhere), never in the project.

## Multi-module projects and workspaces

Start Interlint, and your agent, in the root of either layout:

- **A Maven reactor**: a `pom.xml` with `<modules>`. `init` looks for `@ArchTest` classes in `src/test/java` of every module, and for Checkstyle and PMD in the build of every module.
  - A plugin the parent only declares in `<pluginManagement>` counts when a module turns it on in `<build><plugins>`; one no module turns on is left out. The checks name the executions the parent manages, as in `checkstyle:check@style`.
  - The `architecture` check builds only the modules with the `@ArchTest` classes and the modules they depend on (`-pl launcher -am`), and tells Surefire not to fail in the modules without them (`-Dsurefire.failIfNoSpecifiedTests=false`).
  - `report: archunit` and `report: maven` read the reports of every module and show each source path from the root, such as `infrastructure/src/main/java/com/acme/Order.java:12`.
- **A workspace**: a directory without `pom.xml` that holds several Maven projects, each a single project or a reactor with its own Maven Wrapper, for example as Git submodules. Other projects, such as a Node front end, are ignored. `init` writes the checks of every Maven project it finds up to three levels down, each with its `dir`, and names them after it:

```yaml
# Generated by interlint init.
checks:
  - name: orders/architecture
    dir: orders
    run: ./mvnw -q test -pl launcher -am -Dtest=OrdersArchitectureTest -Dsurefire.failIfNoSpecifiedTests=false -Dcheckstyle.skip -Dpmd.skip
    report: archunit
    when: edit
  - name: orders/checkstyle
    dir: orders
    run: ./mvnw -q checkstyle:check@style
    report: maven
    when: edit
  - name: billing/checkstyle
    dir: billing
    run: ./mvnw -q checkstyle:check@style
    report: maven
    when: edit
```

- `dir` is the directory the check runs in, relative to `interlint.yaml`, so each check uses its own project's `pom.xml`, Maven Wrapper and configuration. Without `dir`, a check runs where `interlint.yaml` is. A `dir` outside that directory is an error. A check whose `dir` does not exist, a typo or a removed Git submodule, fails at every task end with `✗ <check> · its dir "<dir>" does not exist`, changed or not, so the agent and you always see it; the other projects still run. After an edit it is left to task end, so it does not block every edit.
- Violations show their path from the workspace root, such as `orders/infrastructure/src/main/java/com/acme/Order.java:12`.
- After an edit, only the `edit` checks of the project that holds the file run. A file outside every Maven project runs nothing.
- At the agent's task end, only the projects it changed run (see [At task end](#at-task-end)).
